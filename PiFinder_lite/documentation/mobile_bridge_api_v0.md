# Mobile Bridge API v0

Issue: [#20 Add mobile bridge API v0 documentation](https://github.com/oalexx/PiFinder_mobile_sensors/issues/20)

## Purpose

Mobile Bridge API v0 defines the optional HTTP contract between the Android
companion app and PiFinder Lite.

This API must not replace classic PiFinder behavior. It is an additive layer for
mobile status checks, profile upload, GPS handoff, IMU experiments, and future
camera frame upload.

## Base URL

The Android app stores a PiFinder base URL such as:

```text
http://pifinder.local
http://192.168.8.167:8080
http://192.168.8.167:18080
```

Endpoint paths are appended to the base URL:

```text
<base-url>/mobile/status
<base-url>/mobile/profile
<base-url>/mobile/mount_profile
<base-url>/mobile/gps
<base-url>/mobile/imu
<base-url>/mobile/camera_frame
<base-url>/mobile/camera_solve
```

## Versioning

The first API version is named:

```text
mobile-bridge-v0
```

Responses should include an `api` field where practical:

```json
{
  "ok": true,
  "api": "mobile-bridge-v0"
}
```

Breaking changes should create a new API version. Small additive fields are
allowed in v0.

## Common Response Shape

Successful response:

```json
{
  "ok": true,
  "api": "mobile-bridge-v0",
  "message": "accepted"
}
```

Error response:

```json
{
  "ok": false,
  "api": "mobile-bridge-v0",
  "error": {
    "code": "invalid_json",
    "message": "Request body must be valid JSON."
  }
}
```

Recommended HTTP status codes:

- `200`: request succeeded;
- `400`: invalid JSON or invalid field values;
- `404`: endpoint does not exist;
- `415`: unsupported content type.

## GET `/mobile/status`

Status: implemented.

Purpose:

Android uses this endpoint to verify that it is talking to PiFinder and that the
mobile bridge surface is available.

Request:

```http
GET /mobile/status
```

Response:

```json
{
  "ok": true,
  "api": "mobile-bridge-v0",
  "server_time_utc": "2026-05-03T17:00:00Z",
  "pifinder": {
    "web_remote": true,
    "image_endpoint": true,
    "key_callback": true,
    "lx200_port": 4030
  },
  "mobile_bridge": {
    "profile": "implemented",
    "mount_profile": "implemented_read_only",
    "gps": "implemented",
    "imu": "implemented_debug_only",
    "camera_frame": "implemented_storage_only",
    "camera_solve": "implemented_diagnostic_only"

```

Android behavior:

- Call this from `Test Connection`.
- Show success if `ok` is true.
- Show server time/API version for debugging.

## POST `/mobile/profile`

Status: implemented.

Purpose:

Android sends the structured capability/profile JSON generated by the
Compatibility Tester.

Request:

```http
POST /mobile/profile
Content-Type: application/json
```

Example body:

```json
{
  "schema": "pifinder-mobile-profile-v0",
  "created_utc": "2026-05-03T17:00:00Z",
  "app": {
    "version_name": "0.1.0",
    "version_code": 1
  },
  "device": {
    "manufacturer": "samsung",
    "model": "SM-S948B",
    "android_api": 35
  },
  "readiness": {
    "grade": "HIGH",
    "percent": 89
  },
  "sensors": {
    "accelerometer": true,
    "gyroscope": true,
    "magnetometer": true,
    "rotation_vector": true,
    "game_rotation_vector": true
  },
  "cameras": [
    {
      "id": "0",
      "facing": "back",
      "hardware_level": "LEVEL_3",
      "manual_sensor": true,
      "raw": true
    }
  ]
}
```

Response:

```json
{
  "ok": true,
  "api": "mobile-bridge-v0",
  "message": "profile accepted",
  "stored_as": "profile_latest.json",
  "received_utc": "2026-05-03T17:00:01Z"
}
```

Validation rules:

- Body must be JSON object.
- Unknown fields are allowed.
- Endpoint should not use the profile to change runtime behavior in v0.
- Invalid JSON or non-object JSON returns `400` with error code
  `invalid_json`.

Persistence:

```text
~/PiFinder_data/mobile/profile_latest.json
```

## GET `/mobile/mount_profile`

Status: implemented, read-only.

Purpose:

Expose the latest mobile mount profile metadata for diagnostics without feeding
the profile into PiFinder runtime state.

Request:

```http
GET /mobile/mount_profile
```

Runtime profile location:

```text
~/PiFinder_data/mobile/mount_profiles/*.json
```

Response with no profiles:

```json
{
  "ok": true,
  "api": "mobile-bridge-v0",
  "profile_available": false,
  "profile": null,
  "warnings": ["no_mount_profiles_found"]
}
```

Response with a profile:

```json
{
  "ok": true,
  "api": "mobile-bridge-v0",
  "profile_available": true,
  "profile": {
    "profile_id": "SM-S948B-tube-clamp",
    "status": "usable",
    "device_model": "SM-S948B",
    "runtime": {
      "allow_integrator_feed": false,
      "allow_guidance_overlay": false,
      "requires_manual_enable": true
    },
    "safety": {
      "integrator_blocked": true,
      "runtime_usable": false,
      "overlay_candidate": true,
      "read_only": true
    }
  },
  "warnings": []
}
```

Guardrails:

- The endpoint is read-only.
- `allow_integrator_feed` is always reported as `false` even if a profile file
  requests it.
- `runtime_usable` remains `false` in Phase 5.
- Unsafe or incomplete profiles are surfaced through `warnings`.
- This endpoint does not change solver, GPS, IMU, integrator, camera, or
  classic UI behavior.

## Mobile Bridge Debug Persistence

Status: implemented.

PiFinder stores the latest received or generated Mobile Bridge debug payloads
under:

```text
~/PiFinder_data/mobile/
```

Current and planned files:

```text
status.json
profile_latest.json
mount_profiles/<profile-id>.json
gps_latest.json
imu_latest.json
frames/<frame_id>.jpg
frames/<frame_id>.json
```

Writes use a temporary JSON file followed by replace, so readers should not see
partially written payloads.

Persistence is for debugging and validation only. It must not change solver,
integrator, GPS, or classic PiFinder behavior by itself.

Persistence:

```text
~/PiFinder_data/mobile/profile_latest.json
```

## POST `/mobile/gps`

Status: implemented.

Purpose:

Android sends a single GPS fix to PiFinder. In v0 this should be received and
persisted first. Feeding the GPS queue should be explicit later work.

Request:

```http
POST /mobile/gps
Content-Type: application/json
```

Example body:

```json
{
  "lat": 40.4168,
  "lon": -3.7038,
  "altitude_m": 667.0,
  "accuracy_m": 8.0,
  "time_utc": "2026-05-03T17:00:00Z",
  "source": "android-gps"
}
```

Response:

```json
{
  "ok": true,
  "api": "mobile-bridge-v0",
  "message": "gps accepted",
  "stored_as": "gps_latest.json",
  "received_utc": "2026-05-03T17:00:01Z"
}
```

Validation rules:

- `lat` required, numeric, between `-90` and `90`.
- `lon` required, numeric, between `-180` and `180`.
- `altitude_m` optional numeric.
- `accuracy_m` optional numeric and non-negative.
- `time_utc` required non-empty UTC timestamp string.
- `source` required non-empty string.
- Invalid JSON or non-object JSON returns `400` with error code
  `invalid_json`.
- Invalid GPS fields return `400` with error code `invalid_gps`.

Persistence:

```text
~/PiFinder_data/mobile/gps_latest.json
```

Future integration:

- A later explicit option may feed accepted GPS into the existing GPS queue.
- Classic GPSD/UBlox/fake GPS behavior must remain unchanged by default.

## POST `/mobile/imu`

Status: implemented, debug only.

Purpose:

Android sends a bounded IMU/orientation sample batch for offline analysis. v0
must not feed PiFinder's integrator.

Request:

```http
POST /mobile/imu
Content-Type: application/json
```

Example body:

```json
{
  "schema": "pifinder-mobile-imu-batch-v0",
  "batch_label": "mounted_reference",
  "device_time_utc": "2026-05-03T17:00:00Z",
  "capture_duration_ms": 2000,
  "screen_orientation": "portrait",
  "app_version": {
    "package": "io.pifinder.mobile",
    "version_name": "0.1.0",
    "version_code": 1
  },
  "device": {
    "manufacturer": "samsung",
    "model": "SM-S948B",
    "android_api": 35
  },
  "samples": [
    {
      "t_android_ns": 1234567890,
      "sensor": "rotation_vector",
      "values": [0.0, 0.0, 0.0, 1.0],
      "accuracy": 3
    },
    {
      "t_android_ns": 1234567900,
      "sensor": "game_rotation_vector",
      "values": [0.0, 0.0, 0.0, 1.0],
      "accuracy": 3
    }
  ]
}
```

Response:

```json
{
  "ok": true,
  "api": "mobile-bridge-v0",
  "message": "imu batch accepted for debug",
  "stored_as": "imu_latest.json",
  "received_utc": "2026-05-03T17:00:01Z",
  "batch_label": "mounted_reference",
  "sample_count": 2
}
```

Validation rules:

- Body must be a JSON object.
- Either `samples` or `sample` must be present.
- `samples` must be a non-empty list with 512 items or fewer.
- `batch_label` is optional for backwards compatibility and defaults to
  `diagnostic`.
- Accepted `batch_label` values are `diagnostic`, `stationary`, `slew`,
  `mounted_reference`, and `repeat_check`.
- `capture_duration_ms`, when present, must be a non-negative number.
- Each sample must include:
  - `sensor`: non-empty string, for example `rotation_vector` or
    `game_rotation_vector`.
  - `t_android_ns`: non-negative Android sensor timestamp.
  - `values`: 3 to 5 numeric values.
- Invalid JSON or non-object JSON returns `400` with error code
  `invalid_json`.
- Invalid IMU fields return `400` with error code `invalid_imu`.

Persistence:

```text
~/PiFinder_data/mobile/imu_latest.json
```

Important:

- Android sensor coordinate frames are device-relative and are not aligned to the
  telescope optical axis.
- Coordinate frame assumptions must be analyzed before using this for pointing.
- Magnetometer contamination and drift must be analyzed before integrator work.
- This endpoint must not feed PiFinder's integrator in v0.

## POST `/mobile/camera_frame`

Status: implemented, storage only.

Purpose:

Upload one mobile JPEG frame to PiFinder and persist it for debugging. This
endpoint intentionally does not solve the image, feed the integrator, update
pointing, or affect classic PiFinder behavior.

Chosen first request shape:

```http
POST /mobile/camera_frame
Content-Type: multipart/form-data
```

Parts:

```text
frame: JPEG binary file part
metadata: JSON object part encoded as UTF-8 text
```

Example metadata:

```json
{
  "schema": "pifinder-mobile-camera-frame-v0",
  "created_utc": "2026-05-03T17:00:00Z",
  "device": {
    "manufacturer": "samsung",
    "model": "SM-S948B"
  },
  "camera_id": "2",
  "camera_selection": "recommended_SM-S948B_camera_2",
  "format": "jpeg",
  "width": 4000,
  "height": 3000,
  "iso": 3200,
  "exposure_ns": 176094495,
  "focus_diopters": 0.0,
  "orientation_degrees": 90,
  "capture_mode": "solve_candidate_burst",
  "source_file": "pifinder_solve_candidate_burst_20260504_224500_solve_iso3200_001.jpg"
}
```

Response:

```json
{
  "ok": true,
  "api": "mobile-bridge-v0",
  "message": "camera frame stored for debug",
  "frame_id": "20260504T210000Z_a1b2c3d4",
  "stored_frame": "/home/pi/PiFinder_data/mobile/frames/20260504T210000Z_a1b2c3d4.jpg",
  "stored_metadata": "/home/pi/PiFinder_data/mobile/frames/20260504T210000Z_a1b2c3d4.json",
  "bytes": 1234567,
  "received_utc": "2026-05-04T21:00:00Z",
  "elapsed_ms": 42,
  "solver_invoked": false
}
```

HTTP status:

```text
200 OK
```

Validation rules:

- Multipart field `metadata` is required and must be a JSON object.
- Multipart file field `frame` is required and must be non-empty.
- `frame` must start with the JPEG magic bytes.
- `frame` must be 25 MiB or smaller.

Persistence:

```text
~/PiFinder_data/mobile/frames/<frame_id>.jpg
~/PiFinder_data/mobile/frames/<frame_id>.json
```

Rules for this storage-only implementation:

- Do not invoke the solver.
- Do not feed PiFinder's integrator or live pointing state.
- Do not assume mobile-camera solving will work.

## POST `/mobile/camera_solve`

Status: implemented, diagnostic only.

Purpose:

Run the Mobile Camera diagnostic chain against a previously uploaded JPEG frame:
quality score first, then an explicit diagnostic solve attempt only when the
score accepts the frame or a debug override is provided.

Request:

```http
POST /mobile/camera_solve
Content-Type: application/json
```

Example body:

```json
{
  "frame_id": "20260504T210000Z_a1b2c3d4",
  "solve_timeout_ms": 1000,
  "preprocess_modes": "baseline,background_subtract"
}
```

Response when the score rejects the frame:

```json
{
  "ok": true,
  "api": "mobile-bridge-v0",
  "frame_id": "20260504T210000Z_a1b2c3d4",
  "diagnostic_only": true,
  "integrator_updated": false,
  "runtime_pointing_updated": false,
  "score": {
    "grade": "LOW",
    "quality_score": 12.0,
    "accept_for_diagnostic_solve": false
  },
  "solve": {
    "attempted": false,
    "solve_ok": false,
    "skipped_reason": "quality_score_rejected"
  },
  "summary": {
    "status": "rejected",
    "label": "Rejected by quality score",
    "grade": "LOW",
    "quality_score": 12.0,
    "attempted": false,
    "solve_ok": false,
    "skipped_reason": "quality_score_rejected"
  },
  "recommendation": "capture_better_frame",
  "next_action": "Run Full Diagnostic again with a darker, steadier frame or wait for clearer sky.",
  "report": {
    "stored": true,
    "json_report": "/home/pi/PiFinder_data/mobile/camera_solve_reports/<report>.json"
  }
}
```

Validation rules:

- Body must be a JSON object.
- `frame_id` must match a stored upload under
  `~/PiFinder_data/mobile/frames/<frame_id>.jpg`.
- `frame_id` may contain only letters, numbers, underscores, and hyphens.
- Missing or unsafe frame IDs return `400`.
- Successful diagnostic responses include a human-facing `summary`,
  `recommendation`, and `next_action` so Android can display a clear report
  without interpreting low-level solver rows.

Persistence:

```text
~/PiFinder_data/mobile/camera_solve_reports/<timestamp>_<frame_id>.json
```

Report guardrails:

- Reports are local diagnostics and should not be committed unless sanitized.
- Reports remove local frame paths and precise location fields where practical.
- The endpoint never updates PiFinder runtime pointing.
- The endpoint never feeds the integrator.
- The endpoint does not change classic PiFinder solver behavior.

## Security And Trust

v0 is intended for trusted local networks only.

Initial assumptions:

- Android and PiFinder are on the same Wi-Fi/LAN.
- No public internet exposure.
- No authentication beyond the existing PiFinder web environment unless a future
  issue adds token-based protection.

Risks to revisit:

- Anyone on the local network could POST data if endpoints are unauthenticated.
- Camera uploads can consume disk space.
- GPS/IMU data should not silently alter pointing unless explicitly enabled.

## Implementation Guidance

- Keep endpoints under `/mobile/*`.
- Keep handlers small and optional.
- Prefer writing debug payloads first before wiring live behavior.
- Use `~/PiFinder_data/mobile/` for received mobile bridge data.
- Do not alter classic startup defaults.
- Record every original PiFinder code change in
  `PiFinder_lite/documentation/upstream_change_log.md`.
